## 잘한 점

1. **설계를 문서로 먼저 굳히는 습관이 자리 잡았습니다.**
   2020~2022년 사이드 프로젝트는 구조부터 크게 잡고 중간에 멈추는 일이 많았습니다. 2026년에는 용어집, 결정 기록, 설계 질의(GRILL), TODO를 먼저 쓰고 구현합니다. 덕분에 몇 달 뒤에 다시 열어도 왜 그렇게 만들었는지 바로 알 수 있습니다.
2. **본인 배경을 프로젝트에 녹였습니다.**
   경제학 전공은 primacy-index(논문 기반 지역경제 모형)로, 업무에서 쓰는 K8s·helm은 dnfParty 배포로, 사내 LLM Gateway 경험은 mafia-game-web(LangGraph·RAG)과 멀티 에이전트 개발로 이어졌습니다. 따라 만든 프로젝트가 아니라 **본인만 만들 수 있는 프로젝트**가 늘고 있습니다.
3. **검증 기준을 엄격하게 잡습니다.**
   primacy-index의 Sprint 0은 "코드가 있어도 검증이 안 됐으면 완료가 아니다"라는 기준으로, 헤드리스 Godot 실행과 BenchmarkDotNet 통계 측정까지 통과시켰습니다. 진행도 숫자를 부풀리지 않는 태도가 좋습니다.
4. **AI 코딩 에이전트를 도구가 아니라 팀으로 다뤘습니다.**
   Lord-s-Daughter의 역할별 TODO, planner 검증(PASS/WARN/ISSUE), 커밋 접두어 체계는 업무의 AI Harness 설계와도 이어지는 실험입니다. 커밋 1,586개 중 Cursor 370, Claude 360, Codex 228, planner 180, Gemini 98개로 여러 에이전트가 실제로 나눠 일했습니다.
5. **운영까지 해 본 경험이 있습니다.**
   dnfParty는 Docker + Helm 차트 + Nginx Ingress(HTTPS)로 실제 운영했습니다. 개인 프로젝트로는 드문 수준입니다.
6. **저장소를 정리할 줄 압니다.**
   VRChatAINpc에 섞여 있던 던파·ETF·마비노기 코드를 이력을 유지한 채 분리했고, 이력의 비밀값을 지웠고(233MB → 12MB), 진행도 대시보드를 만들어 전체를 한눈에 보게 했습니다.

## 아쉬운 점

1. **마지막 5%에서 멈춥니다.**

   |---|---|---|
   | game-vault | TODO 1개 | 4개월 (2026-07-08) |
   | erebos_academy_survival | POC TODO 1개 | 3개월 (2026-08-10) |
   | sound-to-visual-web | TODO 4개 | 4.5개월 (2026-06-25) |
   | HoloThello | Unity 에디터 UI 연결 (README는 99%, TODO는 79%) | 14개월 (2025-09-02) |

   거의 다 된 프로젝트 네 개가 마무리 직전에 멈춰 있습니다. 남은 일이 대부분 재미없는 일(에디터 연결, 배포, 마무리)이라 새 프로젝트에 밀린 것으로 보입니다.
2. **새로 시작하는 속도가 끝내는 속도보다 빠릅니다.**
   2026년 3월부터 8월까지 거의 매달 새 프로젝트를 시작했습니다(mafia → Lord's Daughter → mabi → sound-to-visual → game-vault·rolling_vantage → erebos → primacy-index). 진행 중으로 분류된 것만 10개이고, 그중 최근 30일 안에 커밋이 있는 것은 0개입니다.
3. **설계 질의가 구현을 앞질렀습니다.**
   erebos는 설계 질의 204개 중 29개(14%), rolling_vantage는 100개 중 32개만 답했습니다. rolling_vantage는 코드가 거의 없이 설계 문서만 있습니다. 문서화는 장점이지만, 답하지 않은 질문이 쌓이면 시작 자체를 막는 짐이 됩니다.
4. **플랫폼을 제품보다 먼저 만들었습니다.**
   game-vault는 Lord's Daughter와 rolling_vantage가 함께 쓸 포털로 만들었는데, 아직 붙은 게임이 하나도 없습니다. 실제 게임이 SDK를 써 보기 전에는 SDK 설계가 맞는지 알 수 없습니다.
5. **커밋 수는 진척이 아닙니다.**
   Lord-s-Daughter는 커밋 1,586개(전체의 60%)지만 도트 그래픽 32/120, 사운드 1/13이 남았고, 중간에 Godot(스크립트 125개, 씬 74개)에서 웹으로 엔진을 바꿨습니다. 에이전트가 코드는 빠르게 만들지만, 그림·소리 같은 에셋 작업이 병목입니다. 로컬 작업 브랜치도 원격과 어긋나 있습니다(push하지 않은 커밋 19개, 받지 않은 커밋 58개).
6. **보여 주기 위한 마감이 없습니다.**
   최근 public 저장소 중 데모 링크, 스크린샷, 릴리스, LICENSE를 갖춘 곳이 없습니다. GitHub를 방문한 사람이 결과물을 직접 볼 방법이 없어서, 들인 노력에 비해 포트폴리오 가치가 낮게 보입니다.

## 제안 (우선순위 순)

1. **진행 중 프로젝트를 2~3개로 줄이세요.** 나머지는 대시보드에서 "보류"로 명시합니다. 보류는 실패가 아니라 선택입니다.
2. **거의 끝난 것부터 공개하세요.** sound-to-visual-web(4개 남음)과 game-vault(1개 남음)를 끝내고, 무료 호스팅에 데모를 올려 README에 링크를 답니다. 출시 경험 한 번이 다음 완주를 쉽게 만듭니다.
3. **game-vault에 실제 게임 하나를 붙이세요.** 가장 작은 게임으로 SDK를 검증합니다. HoloThello의 WebGL 빌드나 sample-game이라도 좋습니다.
4. **Lord-s-Daughter는 체험판 범위를 정하세요.** 10~18세 전체 대신 1년 차만 플레이할 수 있는 버전을 목표로 잡고, 도트·사운드도 그 범위만 만듭니다. 먼저 로컬 브랜치를 원격과 맞추세요.
5. **설계 질의에 기한을 두세요.** 답하지 않은 질의는 "기본값으로 정하고 진행, 문제가 생기면 다시 본다"로 일괄 처리합니다.
6. **public 저장소에 공개 필수 요소를 갖추세요.** 스크린샷·데모 링크·LICENSE·GitHub Actions(테스트 자동 실행)를 추가합니다. 반나절 작업으로 포트폴리오 가치가 크게 오릅니다.
7. **업무가 바쁜 시기에 맞춘 리듬을 정하세요.** 업무 프로젝트가 몰리는 시기에는 "주 1회, 한 프로젝트, TODO 1개" 같은 최소 목표로 맥을 이어 갑니다.
